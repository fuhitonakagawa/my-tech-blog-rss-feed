# RSSフィードの障害調査・復旧

## ユーザーの依頼と作業範囲

次の依頼を一続きの作業として実行する。

> RSS feed生成が失敗しています。GHAの問題か、コードのバグや対応不足か、一過性のものか見て、修正が必要ならPR作ってください。
> PRはそのままマージして、再実行したGHAの結果を確認してください。

このスキルによる復旧の依頼には、必要な作業ブランチ・コミット・push・PR作成、チェック通過後のマージ、復旧に必要なGHA実行、公開結果の確認を含む。各段階で同じ許可を聞き直さない。ユーザーが「調査だけ」「PRまで」「マージしない」などと範囲を狭めた場合は、その指定を優先する。

追加権限やユーザーだけが決められる情報が必要な場合は、独立して進められる調査・実装・検証を済ませ、具体的な不足と必要な操作を伝える。ブランチ保護や必須レビューを回避しない。無関係なPR、履歴の削除、購読先への手動投稿はこの依頼に含めない。

## 1. 対象と現在地を確認する

- 対象は原則 `fuhitonakagawa/my-tech-blog-rss-feed`。ユーザーが別のリポジトリを指定した場合はそちらを使う。GitHubツールのリポジトリ指定、または `gh --repo` を常に明示する。
- ルートの `AGENTS.md` と `README.md`、関連するワークフロー・コード・テストを読む。設定値・公開パス・成功条件は現在の実装から確認する。
- `git status --short`、ローカルHEAD、リモートの対象ブランチ、Actionsの `head_sha` を照合する。既存の変更を保持し、必要なら別worktreeを使う。
- 本番の `generate-feed.yml`、PR/CIの生成、外部テスト、後続のPages公開を区別する。失敗した実行だけでなく前後の成功・失敗も調べ、同じコミットでの再現性を確認する。
- 利用可能なGitHub連携ツールを優先する。能力が足りない操作だけ `gh` やREST APIを使う。ログは保存して失敗箇所と前後を抽出し、巨大な全文や秘密情報を出力しない。

## 2. 原因を段階ごとに切り分ける

対象実行のrun ID、試行番号、コミット、時刻、失敗ジョブ・ステップ、根拠となるエラーを記録する。

| 段階 | 確認する内容 |
| --- | --- |
| GHAの実行基盤 | 起動・待機・キャンセル、checkout、Actions/Artifacts/Cache/API、権限、サービス障害 |
| 実行環境 | Node/npmと固定依存の整合、インストール失敗、翻訳ランタイムの準備 |
| RSS生成 | 取得・解析・集約・翻訳・履歴処理の例外、終了コード、対象ソースの実データ |
| 記事の保存 | 取得済み記事の専用ブランチとバックアップ、保存・復元の成否 |
| 配置 | サイト構築、成果物の取得、`gh-pages`への配置 |
| 公開 | 配置コミットに対応するPagesの実行・試行番号・状態、実URLの内容 |

次の区分は併存することがある。観測事実と推測を分けて説明する。

- **GitHub側の問題**: Actions/API/Pagesのエラーや待機をログから特定する。公開障害情報は補助的な証拠とし、GitHub全体の障害と断定しすぎない。
- **コードのバグ・対応不足**: 同じ入力での再現、未対応形式、境界条件、タイムアウトの不整合、再試行や保存経路の不足を確認する。
- **一過性**: 同じコードで前後や再試行が成功し、永続的な不具合の証拠がない場合。単に次回が成功しただけで、復旧機構の不足を見落とさない。

特に親の確認処理・ジョブ・外部処理の期限を比較する。下流がタイムアウトする前に親が終了すると、再試行コードがあっても動かない。初回・全再試行・バックオフ・起動待ち・公開反映待ちが全体予算に収まるかを確認する。

HTTP 403/429や画像取得の警告を、生成全体の失敗と混同しない。終了コード0でも対象フィードが `stale` / `unavailable` の場合がある。外部テストの「未検証」を取得成功と扱わない。

## 3. 修正するか、再実行で復旧するかを決める

- 一過性で既存の処理が十分なら不要なPRを作らず、同一コードの適切な実行を再試行して公開まで確認する。
- 再試行対象は最新の関連実行に絞る。古い配置の再実行で新しい公開内容を巻き戻さない。現在進行中の復旧や、より新しい本番実行があればそちらを追う。
- コードや設定の修正が必要なら、最新の対象ブランチから専用ブランチを作り、原因に対応する最小限の変更を行う。
- 成功判定を弱めたり、失敗を警告だけに変えたりして緑表示にしない。RSSのGUID・通知日時・公開履歴・取得記事のバックアップを保持する。キャッシュや履歴の一括削除を復旧手段にしない。
- 仕様や操作が変わる場合はREADME、横断的な判断基準が変わる場合はAGENTSを更新する。個別障害の日時・件数・コミットはPRへ記録する。

## 4. 検証してPRを作成・マージする

1. 不具合を再現する回帰テストを追加し、正常系・継続失敗・復旧後も確認する。時間や通信に依存する処理は模擬時刻・API代替で再試行と打ち切りを検証し、実サービスでの結果と区別する。
2. コード変更はREADME指定の内部テスト・lint・依存監査を実行する。ワークフロー変更は構文と権限も検証する。外部取得や生成方式を変えた場合は対象の外部テスト・生成物まで確認する。文書だけならリンク・記述と実装の整合性を確認する。
3. 差分を見直し、無関係な変更や秘密情報がないことを確認する。原因、変更後の動作、検証結果、実行ログへのリンク、残る制約を記載したPRを作成する。
4. 最新のPR先頭コミットに対する必要なCI・レビューとマージ可能性を確認する。チェックが失敗した場合は原因を調べて修正し、一過性なら必要なジョブだけを再試行する。
5. チェック通過後にPRをマージする。対応するAPIでは期待する先頭SHAを指定し、確認後にPRが変わっていたら差分とチェックを再確認する。必須レビュー等で止まった場合は、作成済みPRと具体的なブロッカーを報告する。

## 5. マージ後の実行と公開を最後まで確認する

- マージコミットとリモートの最新コミットを確認する。pushで本番生成が自動起動した場合は、その実行を修正後の再実行として監視し、同じ生成を重複起動しない。
- 自動起動しない場合は、修正を含む最新ブランチの `generate-feed.yml` を手動実行する。失敗ジョブの再実行はその元コミットを使うため、修正前の実行を再試行して検証したことにしない。
- 生成、記事の保存、配置、後続Pages、公開URLを順に確認する。監視中に新しいpushやキャンセルがあれば、コミットを照合して確認対象を更新する。
- 30〜60秒程度の間隔で状態を確認し、進捗を簡潔に伝える。時間のかかる処理の途中で「監視します」とだけ報告して作業を終えない。
- Pagesの成功だけで終了せず、同じ配置コミットの `feeds/delivery/index.json` と公開URLの `schemaVersion`・`updatedAt`・`feeds` を照合する。`gh-pages`ブランチへの配置だけを公開成功と扱わない。
- 公開RSSはHTTP成功とXML解析の両方を確認する。影響が全体に及ぶ場合はマニフェストに含まれる配信先を確認する。対象の生成フィード・集約・画面に変更がある場合は、それぞれの状態・記事・購読リンクも照合する。
- 公開済み `feeds/health/` で取得・掲載の状態も必要に応じて確認する。RSS公開の成功とSlack投稿の確認は別結果として扱う。
- 実行失敗が残ればログを読み、同じ切り分けへ戻る。無制限に再試行しない。外部障害が続く場合は、試した回数、最後のエラー、公開内容の鮮度、未完了の段階を明示する。

## 最終報告

原因の区分と根拠、修正または修正不要の判断、PRとマージ結果、対象コミット・GHAへのリンク、公開RSSで確認した内容を簡潔に報告する。テストだけで確認したこと、実環境で確認できたこと、残る失敗や未検証事項を区別する。呼び出しが終わった後も常時監視しているとは表現しない。
